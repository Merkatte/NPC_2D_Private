# 건물 건설 — 확정 기획과 구조 논의 컨텍스트

> 기록일: 2026-09-27
> 상태: 게임 규칙·구조 확정 후 [상세 구현 계획](Building_Construction_Implementation_Plan.md)을 Plan Mode에서 승인했고 2026-09-27 구현에 착수했다. 구현 완료 기록은 아니다.
> 이 문서는 이번 건설 대화의 확정 규칙과 보류 사항을 소유한다. 현재 구현은 [Builder](../Systems/Builder.md)를 따른다.

## 1. 목적과 현재 범위

플레이어가 지정된 부지에 필요한 시설을 선택하고, 건축가가 자율적으로 공사를 수행하여 완공된 시설을 이용하게 한다. 공간 배치는 미리 설계하면서 시설 종류와 투자 순서는 플레이어의 선택으로 남긴다.

- 첫 대상: 식당, 숙소, 창고, 경비 초소, 농경지.
- 시청은 기존에 배치된 하나를 유지하고 첫 건설 목록에는 포함하지 않는다.
- 일반 시설과 농경지는 여러 부지에 중복 건설할 수 있다.
- 신규 건설과 공사 중 취소를 다룬다. 완공 시설 철거와 업그레이드 동작은 후속으로 보류한다.
- 수리는 이번 구현에 포함하지 않는다. 초기 마을 구성과 자원 지급은 TestOnly 설정으로 마련한다(8.20절).
- 건축가의 현재 구현은 배회·생활 행동·모집까지다. 이 문서의 신규 건설 규칙을 현재 구현 사실로 해석하지 않는다.

## 2. 부지와 플레이어 조작

| 항목 | 확정 규칙 |
|---|---|
| 위치 선택 | 미리 마련된 지정 부지를 사용한다. 자유 배치와 플레이어가 격자 위치를 고르는 방식은 이번 범위가 아니다. |
| 진입 | 빈 부지 클릭 → 건물 목록 → 종류 선택 → 비용 확인 및 건설 확정. 기존 우측 하단 건축 버튼 중심 진입을 대체한다. |
| 기본 선택권 | 현재 모든 부지는 첫 대상 다섯 종류를 모두 허용한다. |
| 부지별 제한 확장 | 기본은 전체 허용이며, 필요한 부지는 건설 가능한 종류의 허용 목록을 지정할 수 있도록 설계한다. 현재 맵에 특정 제한을 적용하는 결정은 없다. |
| 통행 영역 | 건물이 들어설 영역은 빈 부지부터 통행 불가다. 건설·취소·완공에도 통행 영역을 유지한다. |
| 접근 위치 | 부지 외곽에 건축가 작업 위치와 완공 시설의 출입구를 미리 마련한다. 실제 크기·좌표·수는 후속 구조/배선 논의에서 정한다. |

모든 종류를 허용하는 부지에서 각 시설을 배치·이용할 수 있도록 외형과 출입구 구성을 맞춘다. 부지 크기나 위치에 따른 암묵적인 종류 제한을 추가하지 않는다.

## 3. 비용과 공사 표현

- 기본 건설 비용은 골드·목재·석재로 구성한다. 건물별 요구량은 TBD다.
- 건설 확정 시 비용을 즉시 차감한다. 자재를 실제로 운반하는 과정은 없다.
- 확정 시 비용과 대상 상태를 다시 확인하고, 비용이 부족하거나 확정할 수 없으면 자원과 부지 상태를 보존하며 이유를 표시한다.
- 차감 후 부지의 자재 더미는 비용이 투입되었다는 표현이다.
- 건축가가 실제 작업을 시작하면 가림막과 건축 중 표시를 보여준다.
- 누적 작업량에 따라 공사 게이지가 증가하고 완료 시 완성된 시설을 표시한다.
- 농경지는 완공 후 빈 밭으로 전환하여 기존 씨앗 선택·심기 흐름으로 연결한다.

## 4. 공사 취소와 환불

| 시점 | 처리 |
|---|---|
| 실제 작업 시작 전 | 취소 가능, 투입 비용 전액 환불. 건축가가 이동 중이어도 실제 작업 전이면 이 규칙을 적용한다. |
| 작업 시작 후부터 완공 전까지 | 취소 가능, 남은 진행률만큼 자원별 환불. 진행률 30%면 투입 골드·목재·석재 각각 70%를 환불한다. |
| 완공 후 | 공사 취소 대상이 아니다. 완공 시설 철거는 후속 범위다. |

- 취소하면 참여 건축가의 공사와 자리 예약을 해제하고, 다시 건물을 선택할 수 있는 빈 부지로 돌아간다.
- 진행률을 0~1의 `p`로 나타낼 때 작업 시작 후 자원별 환불량은 `floor(해당 공사에 투입한 수량 × (1 - p))`다. 사용자는 자원별 계산 결과의 소수점을 버리는 방식에 동의했다. 예를 들어 목재 3개의 50% 환불은 1개다.
- 작업 시작 전에는 소수점 계산 없이 실제 지불 비용을 전액 환불한다. 차감·환불 대상은 창고별 재고가 아닌 마을 공용 재고다(8.4절). 위 규칙으로 계산한 환불량은 용량을 초과하더라도 모두 반환한다(8.5절).

## 5. 건축가 선택·예약·협업

- 여러 공사가 있으면 먼저 신청된 공사부터 자동으로 선택한다. 플레이어가 공사별 우선순위를 지정하는 기능은 이번 흐름에 포함하지 않는다.
- 앞선 공사의 작업 자리가 모두 차 있으면 다음 공사를 선택한다.
- 건물별 최대 동시 작업 인원을 두며, 구체 인원은 TBD다.
- 건축가는 출발할 때 자리를 예약하고 작업 전환·완료·취소·생활 행동 전환 시 반환한다. 이동 중 예약도 자리 가용성에 반영한다.
- 참여 건축가 각각의 작업량을 그대로 합산한다. 같은 작업 능력이면 2명은 1명의 두 배 속도로 진행한다.
- 건축 작업 능력은 우선 고정값으로 사용한다. 이후 Guard처럼 전용 스탯을 도입할 수 있도록 확장 가능성을 남긴다. 첫 테스트의 초당 작업량과 창고 요구량은 8.21절을 따른다. animation 타격 등 구체 적용 주기의 연결은 아직 미정이다.

## 6. 생활 욕구와 후속 수리 방향

- 공사 중에도 식사·음수·수면이 필요한 상태가 되면 작업을 중단하고 생활 행동을 수행한다. 정확한 판단 연결은 기존 생활 시스템을 확인해 구조 논의에서 정한다.
- 생활 행동 전환 시 작업 자리를 반환하며, 누적 공사 진행도는 유지한다. 다른 건축가가 빈자리를 맡을 수 있다.
- 생활 행동 후에는 공사 신청 순서에 따라 다시 선택한다. 원래 공사장 복귀를 보장하지 않는다.
- 이미 작업 중이면 다른 공사로 전환하기 위해 현재 작업을 버리지 않는다. 생활 욕구 해결은 이 규칙의 예외다.
- 사용자는 적의 건축물 공격 로직에 대한 테스트도 이루어지지 않았다는 이유로 수리를 이번 구현에서 제외했다. 현재 건설 선택·이동 중 판단에 수리 분기를 구현하지 않는다.
- 피해 건물 자동 수리와 작업 시작 전 수리 우선(공사장 이동 중 전환 가능, 실제 작업 중에는 현재 작업 유지)은 후속 기획으로 보존한다. 내구도·수리비·수리 작업량과 중단 규칙은 수리 착수 시 논의한다.

## 7. 후속 확장과 미결정 사항

| 항목 | 상태 |
|---|---|
| 완공 시설 철거 | 기능 확장 가능성만 열어둔다. 이번에는 버튼이나 실제 철거 동작을 구현하지 않는다. 철거 환불과 시설 내 재고·이용자 처리는 TBD다. |
| 업그레이드 | 확장 가능성만 열어둔다. 높은 단계에서 특수자원도 요구하는 방향이며 종류·단계·수치와 업그레이드 실행은 보류한다. |
| 부지별 허용 종류 | 전체 허용 기본값과 선택적 허용 목록 설정을 지원할 수 있도록 설계한다. 철거·업그레이드 보류와는 별도의 확정 확장 요구다. |
| 건설 수치 | 건축가의 고정 작업량과 창고의 첫 테스트 수치는 8.21절에서 확정했다. 다른 건물별 비용·요구 작업량·최대 인원 및 작업 중 욕구 증가량은 TBD다. 전용 스탯 확장은 후속이다. |
| 자원 확보·용량 | 초기 마을과 자원은 TestOnly에서 설정한다. 이번 건설을 위해 목재·석재의 정식 생산/구매 경로를 추가하는 것으로 해석하지 않는다. 구체 시작 재고·기본 용량·창고별 제공량은 TBD다. 용량/입고/환불 규칙은 8.4~8.5절을 따른다. |
| 중단·실패 | 피격, 접근 불가능한 공사, 건축가 비활성화 등의 처리 세부는 구조 논의에서 정한다. |
| 시설 이용 | 완공 시설의 목적지/provider 등록, 중복 시설 선택과 창고 재고 연결은 코드 구조 논의 대상이다. |
| 시청 | 기존 하나 유지. 철거·재건·업그레이드 세부는 이번 확정 범위가 아니다. |

확장 가능성을 남긴다는 이유로 미사용 범용 프레임워크나 후속 gameplay 기능을 선행 구현하지 않는다. 구현 시 필요한 책임 경계를 유지하는 수준부터 논의한다.

## 8. 합의된 코드 구조 — 작성자와 리뷰어 준수 기준

아래 책임 경계는 사용자가 구조 대화에서 동의한 사항이다. 클래스명은 논의용 명칭이며 정확한 선언·파일 배치·메서드 시그니처는 후속으로 정한다. 코드 작성자는 기존 CodeConvention과 관련 Systems 문서에 더해 이 절을 준수하고, 독립 리뷰는 실제 diff에서 이 경계를 확인한다.

### 8.1 부지와 공사 상태 소유

- `BuildingPlot`은 씬에 유지되는 부지 컴포넌트다. 허용 건물 설정, 작업 위치·출입구, 현재 공사 상태와 완공 시설 참조를 가진다.
- `ConstructionState`는 해당 BuildingPlot이 필드로 소유하는 일반 C# 객체다. 별도 GameObject나 공유 SO가 아니다.
- ConstructionState는 선택한 건물 정의 참조, 실제 지불 비용, 누적 작업량, 작업 시작 여부와 작업자 예약 등 해당 공사만의 runtime 정보를 보관한다.
- 건축가는 이 상태의 소유자가 아니다. 건축가가 떠나도 부지가 공사 진행도를 유지하며, 취소·완공 시 진행 중 공사 상태를 정리한다.
- `BuildingDefinition`은 CSV 파싱·검증 결과인 읽기 전용 일반 C# 정의로 구성하며 runtime 진행도·예약을 보관하지 않는다. 원본 수치와 임시 에셋 연결의 분리 원칙은 8.12절을 따른다.

### 8.2 외부 조회와 작업 대상 전달

- BuilderActionSelector에는 씬의 `BuildingPlotRegistry` 참조 하나를 명시적으로 주입한다. 지정 부지 목록은 Inspector에서 연결하는 구성을 사용한다.
- registry는 부지 참조 목록과 후보 조회를 담당한다. 공사 상태를 소유하거나 NPC의 다음 작업을 결정하지 않는다.
- selector는 판단 시 진행 중인 공사를 가진 BuildingPlot의 읽기 전용 후보 목록을 조회한다. 전체 부지의 내부 상태를 복사해서 전달하지 않는다.
- selector는 후보 부지의 공사 신청 순서·작업 가능 여부·예약 자리 가용성을 확인하고 신청 순서대로 선택한다.
- 후보 조회 시 자리가 있어도 실제 예약 요청 시 부지가 다시 검증한다. 예약 실패 시 selector는 다음 후보를 확인한다.
- 건설 action에는 선택한 작업 대상과 해당 공사의 예약 정보만 전달한다. action은 registry나 전체 부지 목록을 검색하지 않는다.
- UI는 기존 IClickPopupSource 흐름으로 클릭한 부지를 전달받는다. 부지에 연결된 클릭 source를 사용하며 UI의 전체 부지 검색을 추가하지 않는다.

### 8.3 변경 권한과 공사 식별

- 외부는 ConstructionState를 직접 수정하지 않는다. BuildingPlot이 필요한 조회 정보를 제공하고, 예약·작업량 추가·취소 요청은 검증되는 부지의 진입점을 거친다.
- 후보 목록을 읽기 전용으로 제공하는 것과 개별 부지 상태의 변경 권한을 구분한다. 참조를 받았다는 이유로 진행도·예약 목록 setter를 노출하지 않는다.
- 부지 참조와 공사 식별을 구분한다. 예약은 어느 공사의 예약인지 식별할 수 있어야 한다.
- 취소 후 같은 부지에서 새 공사를 시작해도 이전 공사의 작업량 전달이나 예약 반환이 새 공사에 영향을 주지 않아야 한다.
- action과 작업 대상 사이의 정확한 계약은 기존 IInteractionProvider의 적합성을 확인한 뒤 정한다. 이 합의만으로 새 domain 전용 interface나 ActionContext 필드 추가를 확정하지 않는다.

### 8.4 마을 공용 재고와 창고의 역할

- 사용자는 창고별로 목재 20개·30개를 따로 소유하는 방식 대신 마을 재고 50개로 통합하는 방식을 선택했다.
- 목표 구조에서 ResourceManager는 마을 공용 자원 API 창구이며, 자신이 소유하는 일반 C# 객체 ResourceInventory가 골드와 아이템의 실제 재고 상태 및 수량 변경을 관리한다(8.6절). 창고마다 같은 수량을 복제하거나 독립 재고를 두지 않는다.
- GoldManager의 잔액·증감과 WarehouseInventory의 창고별 수량·입출고 책임을 ResourceManager로 이관한다. 건설 전용 ConstructionPayment/ConstructionCostProcessor나 골드 전용 GoldWallet은 추가하지 않는다. 기존 소비자와 serialized 참조의 구체 이관 순서는 구현 계획에서 정한다.
- 골드도 공통 재고에 포함하되 창고의 일반 물품 목록에서는 제외하고 별도의 잔액으로 표시할 수 있도록 저장과 표시를 분리한다.
- 각 창고에는 시설 위치·입고 지점·제공 용량 등 시설 책임만 남긴다. UI 표시를 위한 창고별 재고 사본도 두지 않으며, 어느 창고를 조회하든 마을 공용 재고를 읽는다.
- WarehouseDepositPoint는 NPC 봇짐을 공용 재고에 입고하는 역할로 연결을 변경한다. 운반 중 수량은 입고 전까지 NPC 봇짐이 소유하며 공용 재고에 중복 합산하지 않는다.
- 골드는 보관 용량을 차지하지 않는다. 일반 물품은 종류에 관계없이 1개당 용량 1을 사용한다. 특수자원의 세부는 기존 보류 범위를 따른다.
- 완공된 창고들이 제공하는 용량을 합산한다. 공사 중 창고는 용량을 제공하지 않는다. 창고별 제공량과 마을 기본 용량은 TBD다.
- 현재 실제 코드는 GoldManager가 골드 잔액, 각 WarehouseInventory가 아이템 수량을 소유한다. 위 내용은 변경 목표이며 아직 구현하지 않았다.
- 공용 자원 ID와 내부 수량 자료구조는 8.7절을 따른다. 정적 정의의 정확한 필드·파일 형식, ResourceManager의 API와 자원 거래 계약은 후속으로 정한다. 건설 가능 여부·진행률·환불 비율은 건설 영역의 규칙이며 ResourceManager가 결정하지 않는다.
- 창고가 없는 경우의 기본 용량, 창고 비활성화·파괴 시 용량 상실 조건은 TBD다. 용량 초과 시 재고 보존과 입고 제한은 8.5절을 따른다.

### 8.5 일반 입고와 공사 취소 환불

- 일반 물품의 NPC 입고는 남은 용량만큼 수락하고, 수락하지 못한 잔량은 NPC 봇짐에 유지한다. 수락 수량만큼만 봇짐에서 제거한다.
- 공사 취소 시 규정된 환불량은 보관 용량을 초과하더라도 모두 반환한다. 공간 부족 때문에 환불 자원을 소실시키거나 취소를 거부하지 않는다.
- 환불의 전량 반환은 이미 정한 진행률 기반 환불량에 대한 보장이다. 작업 후에도 최초 비용 전액을 환불한다는 의미가 아니다.
- 용량을 초과한 기존 재고는 보존하고, 공간이 생길 때까지 일반 물품의 추가 입고를 차단한다. 용량을 차지하지 않는 골드에는 이 입고 제한을 적용하지 않는다.
- 코드의 거래 계약에서 일반 입고와 환불의 의도를 구분한다. API 형태와 검증/변경 순서는 8.8절을 따른다. 중복 환불 방지와 건설 취소의 전체 상태 전환 절차는 후속으로 정한다.

### 8.6 ResourceManager와 ResourceInventory의 경계

- ResourceManager는 외부에 노출되는 scene component다. 소비자는 조회·입고·지불·환불 등의 ResourceManager API를 통해서만 공용 재고에 접근한다.
- ResourceManager는 일반 C# 객체 ResourceInventory를 내부에 소유한다. 실제 자원 수량의 저장과 변경은 ResourceInventory가 담당하며 Manager에 별도의 수량 사본을 두지 않는다.
- ResourceInventory는 외부 소비자에게 직접 전달하거나 public getter로 노출하지 않는다. 내부 가변 컬렉션도 노출하지 않는다. 조회 결과는 필요한 값이나 변경 권한이 없는 조회용 데이터로 제공한다.
- 창고·UI·건설·모집·거래의 소비자가 내부 재고를 직접 조작하는 우회 경로를 만들지 않는다. 기존 입고 계약과의 연결도 이 경계를 보존해야 한다.
- Manager는 Unity 연결과 외부 API, Inventory는 재고 데이터와 수량 변경을 담당한다. ID/정의 검증과 거래 검증의 배치는 8.8절, 변경 알림은 8.9절, 용량 제공자 관리는 8.10절을 따른다.

### 8.7 자원 ID와 내부 자료구조

- 기존 정수 itemId 체계를 공용 자원 식별자로 재사용하며 골드도 같은 ID 체계에 등록한다. 기존 아이템 ID는 유지한다.
- 골드·목재·석재·농산물·씨앗을 동일한 조회·증감 경로로 처리한다. 별도의 ResourceType enum과 itemId 간 변환표를 만들지 않는다.
- ResourceInventory는 내부 Dictionary<int, int>에 자원 ID별 수량을 보관한다. 이 dictionary 자체를 외부 API로 반환하지 않는다.
- 골드의 용량 미점유와 창고 목록 표시 여부는 자원 정의로 구분한다. 구체 필드·CSV/SO 스키마와 새 ID 배정은 아직 미확정이다.
- 건설 비용은 자원 ID별 수량 dictionary로 전달한다. 공개 API 형태는 8.8절을 따른다.
- 공통 자원 처리를 재사용해 중복 저장소와 변환 코드를 줄인다. 파일 수만을 줄이기 위해 이미 합의한 Manager/Inventory 또는 부지/공사 상태의 책임 분리를 합치지 않는다.

### 8.8 외부 API와 거래 검증·변경

다음 ResourceManager API 형태에 사용자가 동의했다. 세부 실패 사유·빈 입력·수치 한계 정책은 아직 미확정이다.

```csharp
int GetQuantity(int itemId);
bool TryDeposit(int itemId, int quantity, out int acceptedQuantity);
bool TrySpend(IReadOnlyDictionary<int, int> cost);
bool TryRefund(IReadOnlyDictionary<int, int> amounts);
```

- 비용/환불 명세는 자원 ID별 수량 dictionary를 읽기 전용 입력으로 전달한다. 이를 위해 별도 비용 클래스를 신설하지 않는다. 입력 명세와 내부 재고 dictionary는 별개다.
- ResourceManager는 자원 ID 등록 여부를 확인하고 필요한 자원 정의를 연결한다. ResourceInventory는 수량·잔액·용량을 검증하고 실제 수량 변경을 수행한다.
- TrySpend는 ResourceInventory 내부에서 전체 항목 검증 후 전체 차감한다. 어느 항목이라도 지불할 수 없으면 모든 수량을 보존한다. 순차 차감 후 실패 시 되돌리는 방식을 기본 구현으로 삼지 않는다.
- 전체 검증과 차감 사이에 외부 콜백을 호출하지 않는다. 변경 알림은 전체 적용 후 8.9절의 계약을 따른다.
- TryDeposit은 남은 용량에 따른 수락 수량을 반환하며 기존 부분 입고 규칙을 따른다.
- TryRefund는 잘못된 입력의 실패를 표현할 수 있으나 보관 용량 부족으로 거부하지 않는다. 구체 입력 오류 및 정수 한계 처리는 구현 전 확정한다.
- BuildingPlot은 건설 가능 여부와 환불 비율을 판단하고, 성공적으로 실제 지불한 비용의 사본을 ConstructionState에 보관한다. 호출자가 가진 명세의 후속 변경이나 정의 가격 변경이 기존 공사의 환불 기준을 바꾸지 않아야 한다.

### 8.9 재고·용량 변경 알림

- ResourceManager는 단일 `public event Action ResourcesChanged`로 외부 변경을 알린다. 첫 구현은 변경 자원 ID별 내역이나 증감량 payload를 제공하지 않는다.
- ResourceInventory에서 검증·변경을 완료한 뒤 실제 변경이 있을 때 Manager가 한 번 발행한다. 여러 자원을 한꺼번에 지불해도 거래 전체 완료 후 한 번만 알린다.
- 실패하거나 실제 수량·용량 변화가 없으면 발행하지 않는다. 창고 완공 등으로 총용량이 실제 변경된 경우도 같은 이벤트를 사용한다.
- ResourceInventory는 외부 이벤트를 발행하지 않는다. 외부 알림과 구독 대상은 ResourceManager로 한정한다.
- UI는 열릴 때 구독과 최초 조회를 수행하고, 알림을 받으면 필요한 값을 Manager API로 다시 조회한다. 닫히거나 비활성화될 때 구독을 해제한다.
- 재고 표시를 위해 UI가 매 프레임 polling하는 경로를 추가하지 않는다. 재진입·중복 구독 등 세부 lifecycle은 구현 계획에서 이 계약에 맞춰 검토한다.

### 8.10 창고별 용량 제공자 등록

- ResourceManager는 제공자를 식별하는 창고별 용량 등록 정보를 관리한다. 출처 없는 AddCapacity/RemoveCapacity 증감 호출만으로 총용량을 누적하지 않는다.
- 창고 컴포넌트는 자신의 제공 용량과 연결된 ResourceManager 참조를 가진다. 완공 시 등록하고, 같은 창고의 중복 등록은 중복 합산하지 않는다. 등록 해제를 반복해도 용량이 추가로 감소하지 않아야 한다.
- Manager는 제공 용량을 합산하여 ResourceInventory에 총용량을 전달한다. Inventory는 그 용량과 현재 재고를 기준으로 입고 가능량을 판단한다. 등록 정보와 실제 재고 수량의 책임을 혼동하지 않는다.
- 향후 업그레이드 시 해당 제공자의 등록값을 갱신할 수 있는 구조로 둔다. 업그레이드 동작 자체는 이번 범위가 아니다.
- 비활성화·파괴 등 어떤 상태에서 제공자 등록을 해제할지는 미확정이다. 단순 OnDisable에 gameplay 용량 감소를 무조건 연결하지 않는다. 등록 키와 정확한 API는 후속으로 정한다.

### 8.11 용량 방식 재검토 결과

- 슬롯당 99개 방식과 개수/무게 기준 총용량 방식을 비교한 뒤, 사용자는 현재의 개수 기준 총용량 방식을 유지하기로 확정했다.
- 첫 구현은 골드 외 일반 물품 1개당 용량 1이다. 슬롯 수·스택 상한 99개·슬롯별 배치 상태를 저장 제약으로 추가하지 않는다.
- 창고 용량 100은 앞선 용량 방식 비교의 예시이며 확정 수치가 아니다. 이후 확정한 창고의 첫 테스트 제공량은 8.21절의 500을 사용하고 최종 밸런스는 추후 조정한다.
- UI는 아이템별 아이콘과 총수량을 표시할 수 있다. UI가 격자 모양이어도 저장소가 슬롯 단위라는 의미는 아니다. 구체 레이아웃은 미확정이다.
- 자원별 무게·부피는 실제 플레이에서 필요해질 때 검토할 후속 가능성이다. 현재 수치를 다르게 적용하거나 범용 용량 정책 프레임워크를 선행 구현하지 않는다.

### 8.12 건물 수치의 CSV 관리와 향후 로딩 확장

- 사용자는 원래 목적이 CSV에서 데이터를 관리하고 이후 Addressables 같은 로딩 기능의 도입도 시험하는 것이라고 명확히 했다. 앞선 SO 직접 작성 선택은 이 후속 설명으로 정정한다.
- 건물별 비용·요구 작업량·최대 작업 인원 등 수치 원본은 CSV로 관리한다. 동일 수치를 SO에서도 별도로 수동 편집하는 이중 원본은 만들지 않는다.
- CSV는 데이터 작성 형식이고 Addressables는 에셋 로딩 방식이다. CSV 선택을 Addressables 도입의 필수 조건이나 이번 구현 범위로 해석하지 않는다.
- 사용자는 수치는 CSV, 프리팹·아이콘은 건물 ID별 SO 연결 목록, 소비자가 읽는 정의는 일반 C# 데이터로 두는 구성을 일단 허용했다. SO/Inspector 연결을 영구 고정하지 않고 향후 별도 데이터와 로딩 방식으로 분리할 수 있어야 한다.
- 여기서 '소비 데이터'라고 설명한 BuildingDefinition은 CSV를 파싱·검증해 만든 실행 중 조회용 데이터다. C#이나 Inspector에서 수치를 다시 수동 작성하는 원본이 아니다. 건설 비용 등 소비 수치의 작성 원본도 CSV다.
- 후속 설명에서 사용자는 '소비 데이터'가 별도 수동 원본이 아니라 CSV 파싱 결과라는 점을 확인하고 읽기 전용 C# 정의 구성을 확정했다. 다른 기존 기능의 Inspector 수치를 이번 건설 작업에서 전면 이관한다는 범위까지 확정한 것은 아니다.
- BuildingDefinition은 생성 시 값을 설정하고 공개 setter를 제공하지 않는다. 참조형 필드에 readonly만 붙이는 것으로 불변성을 충족했다고 보지 않는다.
- 비용 등의 입력 컬렉션은 복사하여 보관하고, 원본 컬렉션의 후속 변경이 정의에 영향을 주지 않게 한다. 내부 배열/dictionary를 수정 가능한 참조로 노출하지 않는다. 읽기 전용 선언만으로 내부 가변 컬렉션을 직접 반환하는 방식도 피한다.
- 불변 대상은 비용·요구 작업량 같은 공유 정의다. 공사 진행도·예약은 ConstructionState, 현재 재고는 ResourceInventory가 별도의 변경 가능한 runtime 상태로 관리한다.
- 임시 수동 설정이 실제로 필요한 경우 어떤 데이터인지와 향후 이관 대상을 명시하고, 이미 CSV로 관리하는 수치의 수동 복제본은 만들지 않는다.
- gameplay 소비자는 파싱 결과와 안정적인 건물 ID를 이용하며 CSV 파싱이나 SO 연결 목록의 작성 방식에 직접 의존하지 않도록 한다. 구체 로딩·에셋 해석 API와 책임 클래스는 후속으로 정한다.
- 향후 Addressables 도입을 고려하되 이번 합의만으로 패키지 설치·비동기 로더·원격 배포를 구현하지 않는다.

### 8.13 건물 정보·비용 CSV 분리와 공통 ID

- 건물 기본 정보와 건설 비용을 두 CSV로 분리한다. 파일명과 전체 열 목록은 후속으로 정한다.
- 기본 정보는 건물 정의당 한 행이며 buildingId, buildingType, requiredWork, maxWorkers 등의 정보를 가진다. 비용 표는 buildingId, itemId, quantity로 필요한 자원당 한 행을 작성한다.
- 두 CSV에서 같은 건물은 반드시 같은 buildingId를 사용한다. 비용 표 전용 건물 ID나 표시명 기반 연결을 추가하지 않는다. 건물 ID별 SO 에셋 연결도 같은 정의 ID를 기준으로 한다.
- 비용 표의 itemId는 기존 아이템/공용 자원 ID를 그대로 참조한다. 건물 ID와 아이템 ID는 서로 다른 대상의 식별자이며 같은 번호로 강제 통일한다는 의미가 아니다.
- 비용 행을 buildingId로 묶고 itemId별 수량 dictionary로 조합한 뒤 읽기 전용 BuildingDefinition을 만든다. 골드·목재·석재마다 고정 비용 열을 추가하는 스키마는 사용하지 않는다.
- 로딩 시 존재하지 않는 건물·아이템 ID, 중복된 (buildingId, itemId), 잘못된 수량을 검증한다. 기본 정보의 중복 buildingId와 SO 연결 누락 등의 검증 세부도 로딩 계약에서 정한다.
- 건물 정의 ID는 같은 종류를 여러 부지에 건설해도 공유하는 데이터 ID다. 개별 부지와 각 공사의 식별을 대신하지 않는다.
- buildingId는 CSV의 고유 건물 정의 ID이고 기존 BuildingType enum은 시설의 기능 종류다. 사용자는 두 개념을 분리하는 방식에 동의했다.
- 여러 buildingId가 같은 BuildingType을 가질 수 있다. 작은 창고와 큰 창고는 서로 다른 정의·비용·에셋을 가지되 모두 Warehouse 기능을 사용하는 예다. 이 예시 건물과 수치는 이번 콘텐츠 추가를 확정한 것이 아니다.
- 데이터나 외형만 다른 건물 정의는 새 buildingId로 표현하고 그 이유만으로 BuildingType enum 값을 추가하지 않는다. 새로운 기능 종류가 필요한 경우에만 enum 확장을 검토한다.
- buildingId의 구체 숫자 배정과 CSV의 buildingType 표현 형식은 미확정이다. 기존 enum의 직렬화 값을 임의로 재정렬하지 않는다.

### 8.14 DataManager를 통한 건물 정의 조회

- 사용자는 건물 정의 조회를 기존 IDataManager/DataManager에 통합하는 방향에 동의했다. BuildingPlot과 건설 UI 등 소비자는 주입받은 데이터 조회 API를 사용한다.
- 공개 조회 형태는 `TryGetBuildingDefinition(buildingId, out definition)`이며, DataManager가 BuildingDataContext에 위임한다. DataManager에 건물 정의의 사본이나 CSV 파싱 로직을 두지 않는다.
- 기존 CSVParser는 공통 CSV 파싱을 담당한다. 건물 전용 Mapper는 두 CSV의 행 변환·결합·검증을 담당한다.
- BuildingDataContext는 SO로 두며 건물 정보·비용 CSV 에셋 참조와 검증된 읽기 전용 정의의 ID별 조회 데이터를 관리한다. Inspector에서 건물 수치를 다시 입력하는 용도가 아니다.
- ResourceManager는 현재 보유량과 거래 API, DataManager는 불변 정의 조회를 제공한다. gameplay runtime 재고·공사 상태를 DataManager/BuildingDataContext에 넣지 않는다.
- 향후 로딩 방식이 바뀌어도 데이터 소비자는 IDataManager의 정의 조회 경계를 유지한다. 적재 시점·준비 상태·검증 실패 시 공개 범위와 에셋 수명은 별도 논의 대상이다.

### 8.15 건물 정의의 초기 일괄 적재·검증 후 공개

- 사용자는 다른 데이터도 초기화 시 일괄 적재·검증 후 공개하는 방식이라면 건물에도 적용해도 된다고 답했다. 코드 확인 결과 적재 시점과 실패 정책이 통일되어 있지는 않았다.
- ItemDataContext는 ItemInfos/TryGetItemInfo의 최초 조회에서 CSV를 파싱한다. ItemInfoCsvMapper는 파싱할 수 없는 행을 로그 후 건너뛰고 나머지를 반환하므로 전체 검증 성공 후에만 공개하는 방식이 아니다.
- LocalizeData는 최초 TryGetText 호출 때 적재하며, CSV 파싱과 LocalizeKeyValidation이 모두 성공한 뒤 완성된 lookup을 공개한다. 검증 후 일괄 공개는 이미 적용되어 있으나 초기화 시 선적재는 아니다.
- DataManager.Awake는 현재 action cost 참조 dictionary를 구성하며 모든 CSV를 일괄 적재하는 진입점은 아니다.
- 현행과의 차이를 설명한 뒤 사용자는 건물 데이터부터 초기 일괄 적재·검증 후 공개하는 방식에 동의했다.
- 신규 건물 정의는 초기화 시 한 번 적재하고 건물 정보·비용·아이템 ID·에셋 연결 검증에 모두 성공했을 때만 완성된 목록을 조회 가능하게 공개한다. 구성 중인 목록이나 오류 행만 제외한 부분 목록을 공개하지 않는다.
- 적재 중에는 건설 기능을 준비 중 상태로 두고, 검증 실패 시 원인과 파일·행·ID를 진단하며 건설 기능을 사용 불가로 둔다. 정상 준비 완료 후에는 조회 시마다 다시 파싱하지 않는다.
- 기존 모든 데이터가 이미 같은 초기화 정책이라는 전제를 사용하지 않는다. 기존 아이템·지역화의 전체 초기화 정책 변경은 별도 범위이며 자동으로 포함하지 않는다. 건물 검증에 필요한 아이템 조회 등 선행 준비 순서는 명시적으로 구성한다.

### 8.16 부지 상태와 실제 작업 시작 이력

- 사용자는 BuildingPlot의 상태를 Empty, UnderConstruction, Completed의 세 가지로 두는 방식에 동의했다.
- Empty는 건설 가능한 빈 부지다. 비용 지불과 건설 확정이 성공하면 UnderConstruction으로 전환한다.
- UnderConstruction은 등록된 공사의 작업자 대기·이동·작업 중 상태를 모두 포함한다. 공사 취소 시 Empty로 돌아가고 완공 시설 연결이 완료되면 Completed로 전환한다.
- ConstructionState.HasWorkStarted는 실제 작업 시작 이력이다. 비용 지불이나 건축가 이동만으로 true가 되지 않으며, 최초 실제 작업 시작 시 true가 된다.
- 건축가가 생활 행동 등으로 모두 떠나도 HasWorkStarted와 누적 진행도는 유지한다. 현재 작업자 부재를 작업 시작 전의 전액 환불 조건으로 해석하지 않는다.
- UI의 작업자 대기 표시는 시작 이력과 현재 작업 인원에서 도출한다. 작업자 출입만으로 BuildingPlot의 세 가지 상태를 전환하지 않는다.
- 공사 시작 전/후 환불 구분은 이 이력을 사용한다. 최초 작업 시작 시점의 정확한 action 호출과 상태 변경 API는 후속으로 정한다.

### 8.17 BuildAction의 이동·작업과 예약 수명

- 이동·작업 action 분리와 중단 조건의 책임을 비교한 뒤 사용자는 최초 제안인 통합 BuildAction을 채택했다. 하나의 action은 선택된 공사에 참여하는 목적 단위 행동으로 보며 내부에 이동과 작업 단계를 둔다.
- BuilderActionSelector가 공사를 선택하고 출발 전 자리를 예약하며, BuildAction에는 선택된 대상·예약·작업 위치와 실행에 필요한 의존성만 전달한다.
- BuildAction은 기존 NPCPathFollower로 작업 위치까지 이동하고 도착 후 실제 건설 작업을 시작한다. 이동 알고리즘을 복제하거나 공통 MoveAction에 Builder 전용 분기를 추가하지 않는다.
- 부지의 누적 작업량·HasWorkStarted·작업자 예약은 기존 합의대로 BuildingPlot/ConstructionState가 소유한다. BuildAction은 검증된 호출로 작업 시작과 작업량을 전달한다.
- BuildAction은 이동부터 작업 종료까지 예약 반환 책임을 가지며, 완료·중단·실패·pool 반환에서 예약과 경로·도구 표현을 정리한다. Stop/Clear의 반복 및 부분 초기화에도 중복 반환으로 다른 예약을 손상시키지 않아야 한다.
- selector가 action 구성을 끝내기 전에 실패하면 인계되지 않은 예약과 대여한 action을 정리한다. 실제 작업을 시작하지 않은 종료 경로도 정리 대상이다.
- 공사 취소·무효화, 생활 행동 전환과 경로 실패 등에 맞춰 action을 종료/재판단하되, 새로운 공사 대상의 선택은 selector에 남긴다. action이 manager·registry를 검색하여 다음 목표를 고르지 않는다.
- 수리의 이번 제외 결정에 따라 이동 중 수리 전환 조건이나 이를 위한 미사용 확장 프레임워크는 구현하지 않는다. 향후 수리 도입 시 판단·실행 경계를 다시 정한다.
- 전용 건설 이동 action이나 MoveAction→BuildAction queue는 이번 건설의 기본 구성으로 채택하지 않는다. 기존 WorkerNPC queue lifecycle은 유지한다.

### 8.18 완공 시설의 프리팹 생성

- 사용자는 완공 시 선택한 건물의 프리팹을 해당 BuildingPlot 아래에 생성하는 방식을 채택했다. 모든 건물 종류를 부지마다 비활성 상태로 미리 배치하는 방식을 사용하지 않는다.
- 부지의 고정 작업 위치·출입구는 유지하고 공사 중 표현과 완공 시설을 구분한다.
- BuildingFactory가 생성된 시설에 필요한 scene 참조를 주입하고 목적지·상호작용 등록을 마친 뒤 성공 결과를 반환하면 BuildingPlot을 Completed로 전환한다. 책임 분리는 8.22절을 따른다. 초기화·등록 실패 처리의 구체 API와 복구 절차는 구현 계획에서 명시한다.
- 실제 코드 확인 결과 DestinationDB는 BuildingType당 DestinationInfo 하나를 저장하고 같은 종류가 중복되면 마지막 항목으로 덮어쓴다. InteractableManager는 초기 Inspector 목록에서 provider cache를 구성하며 외부 동적 등록 API는 없다.
- 동종 시설의 중복 건설 및 완공 시 동적 생성을 지원하도록 위 등록 경계를 확장한다. 다중 목적지 조회·선택의 합의는 8.19절을 따른다. 프리팹 생성만으로 기존 NPC가 새 시설을 이용한다고 가정하지 않는다.

### 8.19 다중 시설 등록과 가까운 시설 우선 선택

- 사용자는 종류별 다중 시설 등록과 가까운 시설 우선 선택을 함께 확정했다.
- DestinationDB는 BuildingType별 여러 시설 인스턴스를 등록·해제·조회할 수 있도록 확장한다. 같은 종류의 새 시설이 기존 시설을 덮어쓰지 않는다.
- InteractableManager는 완공 시 생성된 시설 provider의 동적 등록·해제 경로를 제공한다. 준비되지 않았거나 무효화된 시설을 정상 이용 대상으로 노출하지 않는다.
- 판단 계층은 같은 용도를 충족하는 이용 가능한 시설 후보 중 NPC에 가까운 시설을 우선 선택한다. 거리 기준은 8.27절의 직선거리를 따른다. 이동에 필요한 경로 검증과 실패 시 재판단은 유지하되 실제 경로 길이를 시설 비교 기준으로 사용하지 않는다.
- selector는 선택된 실제 시설을 대상으로 action을 구성하며, 이동 위치와 상호작용 provider가 같은 시설 인스턴스를 가리키도록 전달한다. 실행 시 BuildingType만으로 다시 조회해 다른 시설로 바뀌지 않게 한다.
- 창고의 다중 등록은 물리적 위치·출입구·이용 가능 여부와 입고 지점에 대한 것이다. 창고별 재고를 다시 분리하지 않으며 어느 창고에서 입고해도 동일 ResourceManager로 전달한다.
- 건설 비용 차감·환불은 물리적 창고 선택 없이 공용 ResourceManager에 요청한다.
- 이 가까운 시설 우선 규칙은 건축가의 공사 배정 순서를 대체하지 않는다. 공사는 기존 합의대로 먼저 신청된 공사부터 빈자리를 예약한다. 수리 우선은 이번 구현에서 제외한 후속 기획이다.

### 8.20 첫 적용 범위: TestOnly 초기 설정과 고정 작업 능력

- 초기 마을 구성·부지와 기존 시설의 테스트 배치·시작 자원 지급 등의 테스트 준비는 TestOnly에 둔다. 실제 설정 값과 적용 씬·배치 범위는 별도로 정한다.
- TestOnly는 production 자원·건설 API를 사용해 초기 조건을 마련한다. 실제 재고 소유는 ResourceInventory에 유지하고 production 코드가 TestOnly에 의존하지 않는다.
- 이 결정은 자동 Play Mode·게임 화면 검증을 요청한 것이 아니다. 기존 자동 검증 제외 원칙을 유지한다.
- 건축 작업 능력은 우선 고정값이며, 어떤 주민 스탯을 계산식에 연결할지는 보류한다. 이후 Guard처럼 전용 스탯으로 연결할 수 있도록 action 내부에 작업 능력을 하드코딩하지 않는다. 정확한 값의 정의 위치와 전달 API는 구현 계획에서 제안한다.
- 건물별 비용·요구 작업량·최대 인원·창고 제공 용량 등의 정의 수치는 기존 합의대로 CSV로 관리한다. TestOnly 시작 조건과 gameplay 정의 수치를 구분한다.
- 사용자는 설명용으로 제시한 창고와 건축가의 수치를 첫 테스트 값으로 채택했고(8.21절), 환불 소수점은 자원별 버림으로 확정했다(4절).

### 8.21 승인된 첫 테스트 수치

사용자는 테스트 값은 CSV에서 조정할 수 있으므로 제시된 예시를 사용하기로 했다. 아래 값은 최종 밸런스가 아니라 첫 테스트 기준이다.

| 대상 | 항목 | 값 |
|---|---|---|
| 창고 | 건설 비용 | 골드 100, 목재 20, 석재 10 |
| 창고 | 요구 작업량 | 100 |
| 창고 | 최대 작업 인원 | 2명 |
| 창고 | 완공 시 제공 용량 | 500 |
| 건축가 | 고정 작업량 | 실제 작업 중 초당 10 |

- 동일 능력의 건축가가 중단 없이 작업하면 1명은 10초, 2명은 5초가 기준이다. 이동·자리 대기·생활 행동 시간은 이 계산에 포함하지 않는다.
- 창고의 비용·작업량·인원·용량은 건물 정의/비용 CSV에 둔다. 건축가의 작업량도 조정 가능한 정의로 전달하며 action 코드에 숫자 10을 하드코딩하지 않는다. 구체 CSV 스키마/정의 위치는 구현 계획에서 명시한다.
- 위 창고용 값을 식당·숙소·경비 초소·농경지에 자동으로 적용하지 않는다. 다른 건물 수치, 작업 중 욕구 증가량, TestOnly 시작 재고와 기본 용량은 아직 미정이다.
- 환불 소수점은 자원별로 버린다. 계산 기준과 작업 시작 전 전액 환불은 4절을 따른다.

### 8.22 BuildingFactory의 완공 시설 조립 책임

- 사용자는 BuildingPlot과 BuildingFactory를 별도 스크립트로 분리하는 방식을 채택했다. 여러 부지는 씬의 Factory 하나를 참조한다.
- BuildingPlot은 공사 상태·진행도·예약과 비용/환불 요청을 관리하고, 완공 조건이 되면 Factory에 정의와 배치 정보를 전달해 시설 생성을 요청한다. 직접 모든 시설의 조립 로직을 가지지 않는다.
- BuildingFactory는 씬 컴포넌트로 프리팹 생성·필요한 scene 의존성 주입·초기화·목적지 및 상호작용 등록을 수행한다. 필요한 Manager/registry는 명시적으로 연결한다.
- Factory는 성공한 시설 참조를 반환하며 Plot이 이를 보관하고 Completed로 전환한다. 각 완공 시설은 이후 자기 기능을 실행한다.
- Factory는 공사 진행도·예약·건설 비용·환불 비율을 소유하지 않는다. 공사 규칙과 시설 조립의 책임을 섞지 않는다.
- 생성/등록 도중 실패하면 Factory가 해당 생성 시도에서 만든 객체와 추가한 등록을 정리하고 실패를 반환한다. 기존의 다른 시설 등록을 지우지 않는다. Plot은 성공 전까지 Completed로 전환하지 않는다.
- 실패 이후 진행도 보존과 명시적 재시도는 8.26절을 따른다. Addressables로 로딩 방식을 바꾸더라도 시설 조립 책임은 이 경계를 기준으로 한다.

### 8.23 예약 객체와 실제 provider의 구분

- 사용자는 IInteractionProvider가 씬에 실제 존재하는 인게임 오브젝트를 위한 명세라는 경계를 명확히 했다. 일반 C# 예약 객체를 provider로 만드는 제안은 철회했다.
- 작업 provider는 실제 BuildingPlot 또는 부지의 작업 컴포넌트가 구현한다. 예약 객체는 부지·공사·예약의 식별과 반환 수명을 다루며 작업 provider를 대신하지 않는다.
- 실제 provider가 예약을 검증하고 작업량을 반영한다. ActionContext의 기존 provider/request 경로를 유지하며, 예약 전달 계약은 8.24절을 따른다.

### 8.24 예약 발급·인계와 작업 요청 계약

- 사용자는 selector가 부지에 예약을 요청하고, 부지가 발급한 예약을 BuildAction에 인계하며, 실제 작업 요청마다 부지가 해당 예약을 검증하는 흐름을 확정했다.
- 일반 C# 예약 객체 ConstructionReservation은 provider가 아니다. 공통 수명 계약은 `IInteractionReservation : IDisposable`과 읽기 전용 `IsValid`로 표현한다.
- InteractionRequest에 선택적인 IInteractionReservation 참조를 추가한다. 기존 요청은 예약 없이 사용할 수 있고 ActionContext에는 건설 전용 필드를 추가하지 않는다. 실제 scene provider와 예약을 포함한 request를 기존 경로로 전달한다.
- selector는 출발 전에 예약과 작업 위치를 받는다. 예약 시점부터 최대 작업 인원을 점유하지만 실제 작업 시작으로 계산하지 않는다.
- BuildAction은 전달받은 위치로 이동한 뒤 같은 예약을 포함하여 작업량을 요청한다. provider는 자기 부지에서 발급한 예약인지, 현재 공사에 속하는지, 아직 유효한 자리인지 매번 확인한다. IsValid 조회만으로 작업 승인을 대신하지 않는다.
- 최초의 유효한 양수 작업량이 반영될 때 HasWorkStarted를 설정한다. 예약·이동·도착만으로 설정하지 않는다. 새 예약 자리가 가득 찬 상태여도 기존의 유효한 예약자는 작업할 수 있다.
- request 복사 시 동일 예약 객체의 참조를 전달하며 request 자체가 예약을 반환하지 않는다. 인계 전 실패는 selector, 인계 후 완료·중단·실패·pool 반환은 BuildAction이 정리한다. Dispose 반복은 안전해야 한다.
- 공사 취소·완료 시 기존 예약을 무효화한다. 같은 부지에서 새 공사를 시작해도 이전 예약으로 작업하거나 새 예약을 해제할 수 없어야 한다.
- 작업 종료 사유를 action에 전달하는 정확한 결과 계약 등 남은 API 상세는 구현 계획에서 명시하며, 기존 InteractionResult에 건설 전용 필드를 임의로 추가하지 않는다.

### 8.25 BuildingPlot의 상태 변경 진입점과 중복 처리 방지

- 사용자는 BuildingPlot이 상태 변경 API에서 허용 상태를 검사하고 처리 중 재진입을 막는 방식을 확정했다. 외부에서 ConstructionState를 직접 수정하지 않는다.
- 건설 확정은 빈 부지·허용된 건물 정의·비용 충족을 확인한 뒤 비용 차감과 공사 상태 설정을 수행한다. 취소는 현재 진행 중인 공사를 대상으로 환불·예약 무효화·빈 부지 전환을 수행한다.
- 작업 반영은 현재 공사에 속한 유효한 예약을 검사한 뒤 작업량 누적과 완공 조건 확인을 수행한다. 상태가 허용하지 않는 반복 요청은 추가 차감·환불·시설 생성을 일으키지 않는다.
- 부지 내부의 처리 중 표시로 변경 요청의 재진입을 거절한다. ResourceManager의 자원 변경 이벤트 콜백에서 다시 부지 변경을 요청하는 경우도 포함한다. 처리 중 표시는 모든 종료 경로에서 해제한다.
- Unity 메인 스레드에서 동기 처리하는 것을 기준으로 하며 별도 작업 큐나 멀티스레드용 lock은 도입하지 않는다. UI 버튼 비활성화와 별개로 부지 API 자체가 중복 처리를 방지한다.
- 이 결정은 재진입과 반복 처리 방지의 책임·방식을 확정한 것이다. 여러 객체에 걸친 변경의 알림 순서 및 실패 시 정리 상세는 구현 계약에 명시한다. 완공 시설 생성 실패 이후의 정책은 8.26절을 따른다.

### 8.26 완공 실패 시 진행도 보존과 추가 작업 없는 재시도

- 사용자는 요구 작업량을 모두 채운 뒤 시설 생성·초기화·등록에 실패하면 추가 작업 없이 완공을 재시도하는 방식을 확정했다. 재시도에 건설 비용을 다시 차감하지 않는다.
- BuildingPlot은 공사 정보와 진행도 100%를 보존하고 UnderConstruction을 유지한다. 시설 조립이 성공하기 전에는 Completed로 전환하지 않는다.
- 기존 예약을 무효화하고 추가 예약·작업을 받지 않는다. 건축가는 해당 공사에서 벗어나 selector를 통해 다음 행동을 선택한다.
- BuildingFactory는 실패한 생성 시도에서 만든 객체와 등록을 정리하고 실패 원인을 반환한다. 공사 정보에는 완공 처리 실패 정보를 보관하며 별도의 네 번째 부지 상태는 추가하지 않는다.
- 매 프레임 자동 재시도하지 않는다. 원인 해결 후 BuildingPlot의 명시적 완공 재시도 API를 통해 Factory에 시설 조립을 다시 요청한다. 이번 테스트 단계의 호출 경로는 TestOnly에서 제공하며 정확한 API 명칭과 오류 표현은 구현 계획에서 명시한다.
- 재시도에도 상태 검사와 재진입 방지를 적용한다. 성공 시 시설 참조를 보관하고 Completed로 전환하며, 실패 시 진행도와 재시도 가능 상태를 보존한다.
- 기존 취소 환불 공식은 유지한다. 진행도 100%에서 취소하면 환불은 0이며, 완공 실패를 이유로 자동 취소하거나 작업량을 되돌리지 않는다.

### 8.27 시설 선택의 직선거리 기준

- 사용자는 후보별 실제 경로 탐색 비용을 고려하여 우선 단순한 직선거리 기준을 채택했다. 실제 경로 길이를 구해 모든 시설을 비교하는 방식은 도입하지 않는다.
- 비교 위치는 NPC의 현재 위치와 각 시설의 실제 상호작용 위치다. 거리 제곱으로 비교하며 전체 정렬 없이 후보를 한 번 순회해 최소 거리 후보를 선택하는 구현을 기준으로 한다. 시설 후보 수 N에 대한 거리 비교 비용은 O(N)이다.
- 같은 거리에서는 등록 순서를 유지한다. DestinationDB는 후보 제공, 선택 계층은 이용 가능 여부와 거리 비교를 담당하며 선택한 시설 인스턴스와 이용 위치를 action에 함께 전달한다.
- 거리 비교와 실제 이동 경로 계산을 구분한다. 선택된 목적지에 필요한 경로 검증·이동 실패 재판단은 유지한다. 경로 검증 시점과 도달 불가 후보의 반복 선택 방지는 기존 내비게이션 계약을 확인하여 구현 계획에 명시한다.
- 이 규칙은 이용 시설 선택에 적용한다. 건축가의 공사 배정은 신청 순서를 유지한다.

### 8.28 구현 계획에서 추가 확정한 사항

- 사용자는 상세 계획을 승인하고 구현을 요청했다. 정확한 API·배치·검증 계약은 [승인 구현 계획](Building_Construction_Implementation_Plan.md)을 함께 따른다. 이 절은 앞선 TBD를 아래 범위에서 해소한다.
- 다섯 시설의 첫 테스트값은 각 골드100·목재20·석재10, 작업량100, 최대2명이다. 시설별 CSV 행은 분리한다. 창고 제공량500, 나머지0이다.
- 건축 작업은 animation hit가 아닌 실제 시간 기준 초당10이다. 이동·작업 중 세 욕구는 각각0.3/초 증가하고 기존 긴급 욕구 기준을 공유한다.
- 판매는 ResourceManager.TryExchange로 일괄 처리한다. 모집·심기·입고·건설은 동기 알림 보류 범위 안에서 도메인/cargo까지 확정한 뒤 ResourcesChanged를 한 번 발행한다. 프레임 말미 일괄 알림 방식은 채택하지 않는다.
- 기본 용량0이며, 창고는 일시 disable에 용량을 유지하고 실제 제거/파괴 때 해제한다. 초과 재고는 보존한다. 수량 overflow는 무변경 실패와 환급 기록 보존으로 처리한다.
- 새 BuildingTest 씬을 FarmerTest 구성에 기반해 만들고 기존 씬은 필요한 자원·목적지 참조만 이관한다. 초기 빈부지6개, 창고1개(500), 건축가2명, Gold1000·Wood200·Stone200·씨앗각5개를 TestOnly로 설정한다.
- 새 농장 작업/초소 순찰은 부지 외곽의 고정 영역을 사용한다. 작물 외형은 내부에 유지한다. footprint/작업영역/입구를 최초 navigation snapshot부터 고정해 완공 때 topology를 변경하지 않는다.
- 자재더미와 가림막은 별도 그래픽 작업자가 전용 스프라이트 두 종으로 제작한다. 완성 건물/망치/UI의 기존 에셋은 재사용한다.
- 기존 itemId1~7 유지, Gold8/Wood9/Stone10. 건물 ID는 Warehouse1/Restaurant2/Inn3/GuardPost4/Farm5로 정한다. 아이템 usesStorage/showInWarehouse와 건물·비용·작업 CSV는 승인 계획의 스키마를 따른다.

## 9. 구현 인계와 검증 경계

사용자는 프로그래머로서 기능뿐 아니라 구조와 구현 방안도 대화로 선택하기를 요청했다. 책임 배치·자료구조·API 계약·상태 변경 방식에 영향을 주는 선택은 대안과 근거를 제시해 합의하고, 제안과 확정을 구분해 기록한다. 코드 작성자가 미결정 구조를 임의로 확정하지 않도록 이 문서를 할당에 포함한다.

완공 시설 조립의 BuildingFactory 분리, 예약 전달과 검증, 부지의 중복 처리 방지, 완공 실패 시 진행도 보존과 재시도, 시설 선택의 직선거리 기준까지 확정했다. 당시 남아 있던 용량 상실 조건, 테스트 씬/데이터/표현의 적용 범위와 세부 API 계약은 이후 승인 구현 계획과 8.28절에서 확정했다. 이미 합의한 구조를 코드 작성자가 임의로 바꾸지 않도록 한다.

사용자는 기술 선택을 다음 번호로 하나씩 논의했다: 1) 예약·작업 API, 2) 상태 변경의 일관성과 중복 처리 방지, 3) 완공 실패 이후 동작, 4) 시설 거리 기준. 이 논의 자체와 구현 승인은 구분하며, 이후 사용자가 상세 계획에 `Implement the plan.`으로 구현을 명시 승인했다.

사용자의 구현 승인 후 코드·그래픽·Unity 배선을 역할별로 위임한다. 작업자와 독립 리뷰어 모두 이 문서 8절과 승인 상세 계획을 필수 계약으로 전달받는다. 자동 Play Mode 및 게임 화면 검증은 제외하고, 컴파일·정적 검사·참조/구조 검증과 사람이 확인할 플레이 항목을 구분한다. 실제 진행·완료는 PROGRESS에 기록한다.
