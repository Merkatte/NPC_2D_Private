## 0. 계획 원칙

- Phase는 기능 목록이 아니라 **플레이 가능한 결과**를 기준으로 종료한다.
- Phase A부터 D까지 순서대로 진행한다.
- 현재 Phase의 종료 조건을 통과하기 전 다음 Phase 기능을 본격 구현하지 않는다.
- 다음 Phase를 위한 인터페이스는 현재 구현에 실제 사용처가 있을 때만 만든다.
- 기획이 `TBD`인 규칙은 임시값으로 조용히 확정하지 않는다.
- 코드가 존재하는 것과 게임에서 검증 완료된 것은 구분한다.

## 1. 현재 기준선

현재 프로젝트에는 NPC, action, selector, action pool, 목적지 판단, CSV 로딩, ScriptableObject 설정과 상호작용 관련 실험 코드가 존재한다. 일부 action은 미완성이고, 씬 참조와 실행 흐름도 최종 수직 슬라이스로 검증되지 않았다.

따라서 현재 상태는 **Phase A 진행 중**으로 본다. 과거 `PROGRESS.md`에 기록된 이전 구조의 전투·모집·UI 작업은 참고 이력이며, 현재 코드와 씬에서 다시 확인되지 않은 기능을 Phase 완료로 계산하지 않는다.

### 현재 우선순위

1. 현재 코드와 문서의 책임 경계를 일치시킨다.
2. 한 주민의 판단→이동→행동→상태 변화→다음 판단 흐름을 완결한다.
3. CSV와 ScriptableObject를 통한 최소 데이터 로딩·검증 경로를 고정한다.
4. 플레이어 또는 개발자가 행동 선택 이유와 결과를 확인하게 한다.
5. Play Mode에서 반복 동작을 검증한 뒤 Phase B로 이동한다.

## 2. 전체 로드맵

```text
Phase A: 살아 움직이는 한 명
  → Phase B: 여러 주민이 만드는 최소 마을
    → Phase C: 성장과 경제가 있는 마을
      → Phase D: 위기와 결말이 있는 완성 게임
```

| Phase | 핵심 질문 | 종료 결과 |
|---|---|---|
| A | 주민 한 명이 스스로 판단하고 행동하는가? | 한 NPC의 완결된 자율 행동 루프 |
| B | 여러 주민을 배치하는 것이 게임이 되는가? | 고용·배치·생산·소비가 연결된 최소 마을 |
| C | 주민의 차이와 성장이 다음 선택을 만드는가? | 성장·거래·모집이 순환하는 운영 게임 |
| D | 운영 결과를 시험하는 목표와 위기가 있는가? | 승리·패배가 가능한 포트폴리오 빌드 |

## 3. Phase A — 살아 움직이는 한 명

### 목표

한 명의 농부가 자신의 상태를 판단하고, 필요한 장소로 이동하고, 업무 또는 대표 욕구 해결 행동을 수행하며, 그 결과를 플레이어가 이해할 수 있게 한다.

### 포함 범위

- 한 종류의 NPC와 한 직업(농부)
- 명시적인 action 실행 상태: 시작, 실행 중, 성공, 실패, 취소, 정리
- 한 곳의 업무 목적지와 한 곳의 욕구 해결 목적지
- 한 종류의 생산 결과
- 한 종류의 대표 욕구(`배고픔` 잠정, GD-001)
- action 완료 후 상태·자원 변화
- 현재 행동, 선택 이유, 실패 이유를 보는 최소 디버그 UI
- CSV → ScriptableObject TextAsset → loader/mapper → runtime definition 흐름
- 잘못된 데이터와 누락된 목적지의 안전한 실패

### 제외 범위

- 다수 주민 고용과 직업 배정 UI
- 요리사와 다단 생산
- 골드, 상인, 경험치, 레벨
- 전투, 치료, 폭동
- 자유 건설과 저장/불러오기

### 작업 묶음

| ID | 작업 | 산출물 | 검증 |
|---|---|---|---|
| A-01 | 핵심 기획 기준선 정리 | `Game_Plan.md`, Phase A 결정 기록 | GD-001과 최소 생산물 확정 |
| A-02 | 현재 NPC 실행 책임 정리 | runner, selector, action, context/state 경계 | selector가 실행하지 않고 action이 선택하지 않음 |
| A-03 | action lifecycle 완결 | 활성 경로의 action 구현과 정리 규칙 | 성공·실패·취소 후 tick·참조가 남지 않음 |
| A-04 | 데이터 경로 고정 | catalog SO, CSV parser/mapper, ID 정의, validation | 정상 데이터 로드 및 중복·누락 데이터 오류 확인 |
| A-05 | 농부 수직 슬라이스 | 판단→이동→생산→상태 반영→재판단 | 같은 루프가 연속 5회 이상 정상 반복 |
| A-06 | 대표 욕구 수직 슬라이스 | 욕구 증가→우선 판단→이동→해결→업무 복귀 | 임계 전후 행동과 복귀가 예상대로 동작 |
| A-07 | 관찰 수단 | NPC/자원/행동 이유 디버그 패널 | 화면 값과 실제 런타임 상태 일치 |
| A-08 | Phase A QA | Play Mode 기록과 결함 정리 | 아래 종료 조건 전부 통과 |

### 종료 조건

- 한 주민이 외부의 반복 클릭 없이 업무와 욕구 해결을 계속 순환한다.
- action의 성공, 실패와 취소가 다음 행동을 막거나 중복 실행을 만들지 않는다.
- 생산 결과와 욕구 변화가 런타임 상태에 정확히 반영된다.
- 목적지 또는 데이터가 없을 때 예외, 제자리 작업, 무한 재시도 없이 원인이 보인다.
- 핵심 수치를 C# 코드 수정 없이 CSV 또는 설정 에셋에서 바꿀 수 있다.
- 명령행 C# 빌드와 Unity Play Mode 검증이 모두 통과한다.

## 4. Phase B — 여러 주민이 만드는 최소 마을

### 목표

플레이어가 여러 주민을 고용하고 농부와 요리사로 배치하여, 원재료 생산→음식 가공→주민 소비가 이어지는 작은 마을을 운영한다.

### 선행 결정

- GD-002: 시설 배치 범위
- GD-003: 목표·최대 주민 수
- GD-004: 최소 모집 비용과 후보 갱신 방식

### 포함 범위

- 다수 주민 생성, 등록, 제거와 독립 상태
- 최소 모집 화면과 주민 고용
- 직업 배정 및 변경
- 농부와 요리사
- 원재료, 음식과 공용 재고
- 생산, 가공, 보관과 소비의 수량 정합성
- 음식 부족으로 생기는 업무 병목
- 주민 목록, 직업, 행동, 핵심 재고를 보는 기본 운영 UI

### 제외 범위

- 무작위 스탯 기반 고용 비용과 네임드 주민
- 경험치, 레벨과 전직
- 가격 변동과 복잡한 상점
- 적 침공과 치료
- 전체 욕구와 폭동

### 작업 묶음

| ID | 작업 | 종료 증거 |
|---|---|---|
| B-01 | 다수 주민 lifecycle과 registry | 생성·제거 후 중복 tick 또는 유실 참조 없음 |
| B-02 | 공용 아이템·재고 모델 | 생산·이동·소비 전후 총량 일치 |
| B-03 | 농부 생산 완성 | 원재료가 정의된 재고 소유자에게 들어감 |
| B-04 | 요리사와 레시피 | 재료가 있을 때만 음식 생산, 원자적 수량 갱신 |
| B-05 | 음식 소비 | 음식이 있을 때 회복, 없을 때 실패 이유 표시 |
| B-06 | 모집 | 성공 시 한 번만 비용 차감·합류, 실패 시 상태 보존 |
| B-07 | 직업 배정 | 배정 변경 후 기존 action 안전 취소 및 새 역할 수행 |
| B-08 | 기본 운영 UI | 주민과 재고의 현재 상태를 플레이어가 읽고 조작 가능 |
| B-09 | Phase B QA | 최소 마을 시나리오 반복 검증 |

### 종료 조건

- 플레이어가 주민을 최소 두 직업에 배치할 수 있다.
- 농부의 생산물이 요리사의 입력이 되고, 음식이 주민의 욕구 해결에 사용된다.
- 주민 수나 직업 배치를 바꾸면 생산 병목이 관찰 가능하게 변한다.
- 재고 부족, 시설 누락, 직업 변경 상황에서 수량 유실과 action 중복이 없다.
- 고용부터 배치, 생산과 소비까지 하나의 플레이 세션에서 끊김 없이 동작한다.

## 5. Phase C — 성장과 경제가 있는 마을

### 목표

주민의 능력 차이와 성장이 생산 결과에 의미를 만들고, 생산물 판매와 골드가 새 주민 고용 및 다음 투자로 이어지게 한다.

### 선행 결정

- GD-005: 성장으로 달라지는 첫 성과
- GD-006: 네임드 주민의 핵심 가치
- GD-010: 저장/불러오기 필수 여부

### 포함 범위

- 소수의 명확한 주민 스탯과 업무 성과 반영
- 직업 경험치와 레벨
- 최소 상인 또는 거래 UI
- 생산물 판매, 물품 구매와 골드
- 스탯 기반 일반 주민 후보와 고용 비용
- 최소 수의 네임드 주민 데이터
- 밸런스 값을 CSV 중심으로 조정하는 흐름
- 필요 시 최소 저장/불러오기

### 제외 범위

- 복잡한 전직 트리와 다수의 특화 직업
- 동적 시장, 대출, 세금, 외교
- 다수 상인 세력과 호감도
- 방대한 장비와 제작 품질 시스템

### 작업 묶음

| ID | 작업 | 종료 증거 |
|---|---|---|
| C-01 | 스탯과 성과 | 서로 다른 스탯이 한 업무에서 예측 가능한 차이 생성 |
| C-02 | 직업 경험치와 레벨 | 유효 업무만 성장시키며 상한·요구량 규칙 준수 |
| C-03 | 골드와 거래 | 거래 전후 재고와 골드가 원자적으로 일치 |
| C-04 | 후보 생성과 비용 | 고정 시드 재현 및 스탯 기반 비용 설명 가능 |
| C-05 | 네임드 주민 | 고정 ID·외형·능력과 중복 정책 준수 |
| C-06 | 데이터 밸런싱 | 코드 변경 없이 후보·가격·성장 수치 조정 가능 |
| C-07 | 저장 판단 또는 구현 | GD-010 결정 기록 및 필수 시 왕복 검증 |
| C-08 | Phase C QA | 성장→판매→고용의 반복 루프 검증 |

### 종료 조건

- 주민 선택과 직업 배치에 스탯 차이가 실제 의미를 가진다.
- 업무 반복이 성장으로 이어지고, 성장 결과가 UI와 성과에 보인다.
- 생산물을 팔아 얻은 골드로 새 주민을 고용할 수 있다.
- 일반·네임드 후보가 데이터로 추가 가능하고 기존 코드를 수정하지 않는다.
- 경제가 막혔을 때 플레이어가 원인을 재고·생산·비용 정보로 파악할 수 있다.

## 6. Phase D — 위기와 결말이 있는 완성 게임

### 목표

플레이어가 성장시킨 마을과 주민이 외부 위기를 견디고, 명확한 승리 또는 패배에 도달하는 완성된 포트폴리오 빌드를 만든다.

### 선행 결정

- GD-007: 침공 시작 조건
- GD-008: 사망 포함 여부
- GD-009: 최종 승리 조건과 목표 플레이 시간

### 포함 범위

- 경비 직업과 최소 전투 행동
- 한 종류 이상의 적과 최소 웨이브 흐름
- 전투 인력과 생산 인력 사이의 배치 선택
- 핵심 시설 또는 마을 상태에 기반한 패배 조건
- 부상·전투 불능 등 확정된 피해 상태
- 치료 후 업무 복귀
- 최종 목표와 승리 화면
- 시작 안내, 핵심 피드백, 밸런스, 오류 처리와 성능 정리
- 배포 가능한 빌드와 대표 플레이 영상/스크린샷

### 조건부 또는 보류 범위

- 주민 영구 사망
- 성곽 건설·수리
- 여러 종류의 적과 보스
- 전직과 특화 직업
- 갈증·피로·무료함 전체 구현
- 불쾌와 폭동

위 기능은 핵심 승리·패배 루프가 완성된 뒤 일정과 재미에 따라 선택한다.

### 작업 묶음

| ID | 작업 | 종료 증거 |
|---|---|---|
| D-01 | 경비와 전투 | [Guard 구현 계획](./Guard_Action_Implementation_Plan.md)의 탐색→이동→공격→복귀 lifecycle 정상 |
| D-02 | 침공과 표적 규칙 | 동일 조건에서 이해 가능한 웨이브와 표적 선택 |
| D-03 | 피해와 패배 | 모순 없는 상태 전환과 한 번만 발생하는 게임오버 |
| D-04 | 치료와 복귀 | 치료 중 업무 중단, 완료 후 점유 해제·복귀 |
| D-05 | 승리 조건 | 플레이어가 목표 진행과 달성 이유를 확인 가능 |
| D-06 | 온보딩과 피드백 | 처음 플레이한 사용자가 핵심 루프 수행 가능 |
| D-07 | 밸런스와 성능 | 목표 주민·적 수에서 정한 성능과 난이도 통과 |
| D-08 | 최종 회귀와 빌드 | 전체 핵심 시나리오 및 배포 빌드 검증 |

### 종료 조건

- 새 게임 시작부터 주민 고용, 배치, 생산, 성장, 거래, 방어와 결말까지 진행할 수 있다.
- 플레이어가 왜 이기거나 졌는지 UI를 통해 이해할 수 있다.
- 전투 실패가 즉시 복구 불가능한 버그 상태를 만들지 않는다.
- 핵심 데이터 누락, 저장 데이터 오류와 씬 참조 누락을 안전하게 처리한다.
- 목표 환경에서 빌드가 실행되고 핵심 회귀 시나리오가 통과한다.

## 7. 공통 Definition of Done

모든 작업은 다음 조건을 만족해야 완료로 기록한다.

- 작업이 현재 Phase의 목표 또는 결함 수정에 직접 기여한다.
- 관련 `TBD`가 해소되었거나 의도적으로 연기되었다.
- 책임과 의존 방향이 `ProjectStructure.md`, `ARCHITECTURE.md`, `CodeConvention.md`와 일치한다.
- gameplay 수치와 정적 정의가 적절한 데이터 소유자에게 있다.
- 필수 참조 누락 시 처리되지 않은 예외나 무한 반복이 없다.
- action은 성공·실패·취소 시 자신이 변경한 상태를 정리한다.
- 명령행 C# 빌드 또는 Unity 컴파일이 오류 없이 완료된다.
- 런타임 기능은 Unity Play Mode에서 검증한다.
- 완료 내용, 검증 결과와 남은 문제를 `PROGRESS.md`에 기록한다.

## 8. QA 체크포인트

| Checkpoint | 검증 질문 | 통과 조건 |
|---|---|---|
| QA-A | 주민 한 명이 정말 자율적으로 살아 움직이는가? | 판단·이동·업무·욕구·복귀 반복, 원인 표시, 안전 실패 |
| QA-B | 여러 주민의 배치가 작은 운영 게임을 만드는가? | 모집·두 직업·생산·가공·소비 연결 및 수량 정합성 |
| QA-C | 성장과 경제가 다음 선택을 만드는가? | 스탯·성장·판매·골드·고용의 순환과 데이터 확장성 |
| QA-D | 시작과 끝이 있는 완성 게임인가? | 위기·치료·승리·패배·온보딩·빌드 전체 통과 |

## 9. 실행 지침

1. `PROGRESS.md`의 진행 중 작업과 실제 작업 트리를 먼저 확인한다.
2. 현재 Phase에서 의존성이 충족된 가장 작은 수직 작업을 선택한다.
3. 작업이 다른 Phase에 속하면 현재 Phase를 우회할 이유가 있는지 먼저 확인한다.
4. 상세 규칙이 없으면 `SPEC.md`에 확정 내용을 기록하거나 질문을 남긴다.
5. 구조 변경은 관련 구조 문서를 먼저 또는 같은 작업에서 갱신한다.
6. 기능을 코드로만 만들지 말고 관찰·조작·검증 경로까지 포함한다.
7. Phase 마지막 작업 후 해당 QA 체크포인트를 통과하기 전 다음 Phase로 넘어가지 않는다.

## 10. 변경 관리

- 핵심 판타지, 플레이어 권한, 제품 범위가 바뀌면 `Game_Plan.md`를 먼저 갱신한다.
- 기능 규칙과 acceptance criteria가 바뀌면 `SPEC.md`를 갱신한다.
- Phase 순서, 의존성, 종료 조건이 바뀌면 `PLAN.md`를 갱신한다.
- 책임, 데이터 소유권과 의존 방향이 바뀌면 `ProjectStructure.md` 또는 `ARCHITECTURE.md`를 갱신한다.
- 실제 구현 상태는 `PROGRESS.md`에만 기록한다. 계획 문서에 구현 완료를 추측해 적지 않는다.
- 폐기된 요구사항은 삭제만 하지 말고 제외 또는 대체 이유를 남긴다.
