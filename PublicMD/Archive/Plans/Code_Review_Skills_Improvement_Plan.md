## 1. 이 문서의 사용 방법

이 문서는 코드 평가 스킬 개선 대화의 합의와 구현 결과를 보존하는 단일 기록이다. 아래 합의를 기준으로 스킬을 작성했으며 완료 결과는 10절에 기록했다. 현재 실행 지침은 연결된 스킬이 소유한다. 후속 정책 변경 시 이 합의 기록을 참고하되 같은 내용을 별도 계획서나 인계 문서에 복제하지 않는다.

문서 기록 요청은 스킬 수정 요청과 구분한다. 사용자가 실제 작성을 요청하면 확정된 범위와 아래 미정 사항을 확인하고, 그 작업에 필요한 결정만 보완한다. 기존 프로젝트의 작업·승인 규칙은 그대로 적용한다.

개선 대상은 `reviewing-npc-work-code`다. `.codex`가 정책 원본을 소유하고 `.agents`의 기존 진입점은 원본을 연결하도록 변경했다.

## 2. 평가의 목적과 합의한 구성 방향

평가는 구조가 적절한지, 기존 코드와 일관적인지, 비슷한 기능이 이미 존재하는지, 책임이 겹치는지, 컨벤션에 어긋나는지를 근거로 판단한다. 좋은 부분도 근거를 제시하고, 문제는 고칠 위치와 이유가 드러나도록 설명한다. 기존 구현과 같다는 이유만으로 좋은 구조라고 판단하거나, 코드가 비슷하다는 이유만으로 통합을 요구하지 않는다.

큰 평가에서는 영역별 전문성을 활용하되, 작은 평가마다 모든 담당 에이전트를 투입하지 않는 방향으로 진행한다.

- 공통 평가 기준은 한 곳에서 관리한다. 영역 스킬마다 같은 기준을 복제하지 않는다.
- 영역별 스킬은 해당 영역의 문서 진입점, 책임 경계와 특화 관점을 제공한다. 현재 구조 전체를 스킬에 다시 옮기지 않는다.
- `reviewing-npc-work-code`는 평가 범위 설정, 필요한 담당 배정과 결과 통합을 맡는 방향이다. 구현 작업 조정은 `orchestrate-unity-work`의 책임으로 유지한다.
- 스킬을 나누는 것과 실행 에이전트를 나누는 것은 별개다. 분담 여부는 아래 4절의 기준으로 판단한다. 고정된 동시 투입 수는 정하지 않았다.
- 통합 담당은 경계 누락, 중복 지적, 상충하는 권고와 근거를 확인한다. 모든 파일을 처음부터 다시 평가하는 절차를 기본으로 만들지 않는다.

영역 구분은 [Systems](../../Systems/README.md)의 주 소유 관계를 출발점으로 한다. 초기에는 아래 여섯 영역을 사용하고, 책임이 모호한 포괄적 `Core` 담당을 별도로 만들지 않는 방향이다. 아래 표는 합의한 구성 방향이며, 실제 영역별 질문과 문서 연결은 10절의 전문 스킬에 반영했다.

| 영역 | 담당 범위의 출발점 |
|---|---|
| NPC | 공통 NPC 실행·선택·큐와 action lifecycle, 이동 실행, 생성·풀링·표현 |
| Combat | 감지·타깃·공격·피해, 경비병·적과 방어 |
| Economy | 농업, 인벤토리·운반·창고·공유 자원·거래 |
| Settlement | 건설·주거·모집 |
| World | 내비게이션·공간 조회·목적지와 provider 공통 계약 |
| UI | 공통 입력·표시 수명주기, UI 기반 구조·공통 뷰·현지화·카메라 |

기본 주 담당은 Systems leaf의 주 소유 관계로 선택한다. 예를 들어 창고 UI는 Economy의 기능 책임을 중심으로 보고, 필요한 경우 UI 공통 계약을 함께 확인한다. 파일명이나 코드 폴더만으로 담당을 정하지 않는다. 문서의 소유 관계 자체가 부적절하면 그 점도 평가할 수 있다.

이 구성이 실제 결함 발견이나 비용 절감에 얼마나 도움이 되는지는 아직 입증하지 않았다. 향후 실제 평가 결과를 통해 중복 지적, 누락과 통합 비용을 보고 조정한다. 이 기록을 위해 전체 코드 평가나 검증 도구 개발을 시작하지 않는다.

## 3. 운영 항목 1 — 평가 범위와 깊이: 합의 완료

평가 범위와 깊이는 별도로 정한다. 전체 프로젝트를 대상으로 한다고 해서 개괄 평가가 되는 것은 아니다.

### 평가 범위

| 범위 | 의미 |
|---|---|
| 전체 프로젝트 | 프로젝트 전체를 평가 대상으로 삼음 |
| 선택 영역 | NPC·UI 등 지정한 하나 또는 여러 영역을 평가 |
| 특정 대상 | 지정 기능·파일·변경분과 판단에 필요한 관련 코드를 평가 |

범위는 주 평가 대상을 뜻하며, 그 밖의 코드 열람을 금지하는 경계가 아니다. 구체적인 판단에 필요한 호출자·의존 관계·유사 구현은 함께 확인한다. 이를 이유로 관련 없는 영역까지 전체 평가하지 않는다.

### 평가 깊이

| 깊이 | 용도와 결과 |
|---|---|
| 상세 평가 — 기본 | 대상이 정해졌을 때 실제 코드와 관련 근거를 확인하고 구조·일관성·중복·책임·컨벤션을 구체적으로 판단 |
| 개괄 평가 — 선택 | 어디부터 평가할지 모를 때 주요 구조와 기존 평가 기록을 살펴 상세 평가의 우선 대상과 이유를 제안 |

- 대상이 명확하면 상세 평가로 바로 진행한다. 개괄 평가를 필수 선행 단계로 넣지 않는다.
- 개괄 평가는 특히 아직 평가하지 않은 영역 중 어디부터 볼지 정할 때 사용한다.
- 개괄 평가에서 문제를 찾지 못했다고 해당 영역을 상세 평가 완료 또는 통과로 표시하지 않는다.
- 요청이 명확하면 매번 평가 모드를 다시 묻지 않는다. 해석 차이가 실제 범위를 바꾸는 경우에만 확인한다.
- 결과에는 실제 확인한 범위와 미평가 범위를 구분한다. 상세 평가가 일부만 끝났다면 나머지를 밝히고 전체 완료로 보고하지 않는다.

### 자주 사용하는 요청 예시

| 사용자 상황 | 적용 방식 |
|---|---|
| 전체 영역을 상세히 평가해 보고서 아티팩트를 만들고 싶음 | 전체 프로젝트 × 상세 평가. 보고서 형식 자체가 평가 깊이를 결정하지는 않음 |
| 방금 생성·수정한 코드가 프로젝트에 잘 어울리는지 확인하고 싶음 | 변경분 × 상세 평가. 관련 호출자·기존 유사 구현·책임 경계를 함께 확인 |
| 테스트 중 특정 기능이 의심되어 그 부분을 확인하고 싶음 | 해당 기능 × 상세 평가. 관련 경로를 추적하고 관찰된 증상과 확인된 원인을 구분 |
| 아직 평가하지 않은 영역 중 어디부터 볼지 모르겠음 | 개괄 평가로 상세 평가의 우선 대상을 선정 |

## 4. 운영 항목 2 — 에이전트 분담 기준: 합의 완료

평가할 양이 충분히 크고 각 담당이 독립적으로 판단할 수 있을 때 분담한다. 여러 영역이 관련됐다는 이유만으로 에이전트를 나누지 않는다. 아래 세 항목은 서로 다른 평가 유형이 아니라, 같은 작업에 순서대로 적용하는 판단 기준이다.

1. **나눌 수 있는가?** 각 담당에게 독립적인 평가 질문과 주 평가 책임을 줄 수 있어야 한다. 담당 영역 밖의 코드를 읽지 말라는 뜻은 아니다. 판단에 필요한 연결 코드는 함께 확인한다.
2. **나눌 만큼 일이 있는가?** 각 부분에 별도 담당의 조사·보고·통합 비용을 감수할 만큼 조사량이 있어야 한다. 몇 줄의 호출 관계 확인은 주 담당이 함께 처리한다.
3. **나누는 비용이 더 크지는 않은가?** 나눠도 조사의 대부분이 같은 코드와 실행 흐름을 다시 추적하는 일이라면 한 명이 맡는다. 각자 독립적으로 조사하고 연결 경계에서 결과를 맞출 수 있다면 분담하기 좋다. 일부 연결 코드의 공동 확인은 자연스럽다.

### 적용 예시

| 상황 | 적용 방식과 이유 |
|---|---|
| 새 NPC 행동 코드가 기존 구조에 맞는지 평가 | 한 명이 관련 영역 스킬을 참고해 변경과 주변 관계를 함께 평가 |
| 창고 UI의 잘못된 수량 표시를 조사 | 한 명이 Economy와 UI 사이의 문제 경로를 추적. 연결된 영역 수만으로 분담하지 않음 |
| NPC와 전투 영역을 각각 상세 평가 | 각각 독립적인 조사량이 충분하면 영역별 담당으로 분담 |
| 프로젝트 전체를 상세 평가해 보고서 작성 | 영역별로 분담하고 결과를 통합. 모든 영역을 반드시 동시에 실행한다는 뜻은 아님 |
| 미평가 영역의 평가 우선순위를 정하는 개괄 평가 | 기본적으로 한 명이 진행 |

“NPC 모집 UI와 시스템을 개편했으니 확인해줘”라는 요청에서는 UI 관점의 입력·화면 갱신·창 수명주기와 모집 시스템 관점의 모집 조건·비용 차감·NPC 생성 책임을 독립적인 질문으로 나눌 수 있다. 실제 담당은 Systems 주 소유 관계를 따른다. 이 예시는 모집 기능 UI의 소유권을 UI 영역으로 옮긴다는 뜻이 아니다.

질문을 나눌 수 있어도 변경이 버튼 하나와 모집 함수 몇 줄이라면 한 명이 함께 평가한다. 여러 화면과 모집 조건·자원 처리·생성 흐름이 크게 바뀌었다면 분담할 이유가 있다. 반대로 “한 번 클릭했는데 NPC가 두 명 생성된다”처럼 양쪽 담당이 동일한 이벤트부터 생성까지 대부분 같은 경로를 조사해야 한다면 한 명이 전체 흐름을 보는 편이 낫다.

### 분담과 통합 운영

- 전문 스킬 수와 에이전트 수를 일치시키지 않는다. 한 담당이 여러 영역 스킬을 참고할 수 있다. 한 영역의 평가만 커도 독립된 하위 기능별로 분담할 수 있다.
- 평가 도중 예상보다 커졌다면 분담할 수 있다. 이미 확인한 범위와 근거, 아직 확인하지 않은 질문을 인계하여 처음부터 같은 평가를 반복하지 않는다.
- 통합 담당은 경계에서 빠진 책임, 중복 지적, 서로 모순되는 권고와 근거를 확인한다. 추가 조사는 확인이 필요한 구체적인 쟁점에 한정한다.
- 파일 수나 코드 줄 수에 따른 일률적인 분담 기준, 고정 투입 수는 현재 정하지 않는다. 분담 기준 합의에 필수적인 수치로 취급하지 않는다.

## 5. 운영 항목 3 — 책임 경계의 세부 운영: 합의 완료

여러 영역이 연결된 기능은 주 담당을 정하고, 다른 담당에게 필요한 평가 질문을 맡긴다. 주 담당은 해당 기능의 평가를 취합하고 빠진 부분을 확인한다. 실제 에이전트 분담 여부는 4절을 따른다. 규모가 작다면 한 명이 여러 관점을 함께 확인한다.

### 책임 경계의 네 가지 규칙

1. **주 담당은 기능의 책임으로 정한다.** Systems leaf의 주 소유 관계를 출발점으로 삼는다. 화면에 NPC가 등장한다는 이유로 NPC 담당이 전체를 맡거나, 화면이 있다는 이유로 UI 담당이 모집 규칙까지 소유하지 않는다. 문서의 책임 배치 자체가 부적절하면 평가 결과에서 근거와 함께 문제로 제시할 수 있다.
2. **필요한 다른 영역을 읽되 주 평가 책임을 무작정 넓히지 않는다.** UI 담당은 화면 갱신을 판단하려고 모집 시스템을 읽을 수 있다. 그 과정에서 모집 비용 처리의 결함을 발견하면 근거와 함께 주 담당에게 전달한다. 그 발견만으로 모집 시스템 전체를 별도로 평가하지 않는다.
3. **영역 사이의 연결에도 평가 담당을 지정한다.** “모집 결과가 UI에 전달되고 반영되는 계약”처럼 경계의 평가 질문을 명시한다. 주 담당이 누락 여부를 챙기고, 전문 판단이 필요하면 해당 담당에게 맡긴다. 각 영역 내부만 확인하고 연결은 다른 담당이 봤을 것으로 가정하지 않는다.
4. **중복 지적과 상충하는 의견은 근거로 정리한다.** 같은 결함은 하나의 지적으로 합치고 근거를 모은다. 증상이 같아도 원인이 다르면 별도 문제로 유지한다. 책임 배치 권고가 충돌하면 실제 책임·호출 관계·공통 규칙을 확인한다. 근거만으로 결론 내릴 수 없는 설계 선택은 미결정 사항으로 남기며, 통합 담당의 취향으로 확정하지 않는다.

### NPC 모집 UI와 시스템 개편의 예시

| 담당 | 주 평가 질문 |
|---|---|
| Settlement — 주 담당 | 모집 조건·비용·생성 요청의 흐름이 적절한가? 모집 기능 전체의 책임이 빠지거나 겹치지 않는가? |
| UI — 필요할 때 참여 | 입력·이벤트 구독·화면 갱신·창 수명주기가 공통 UI 구조에 맞는가? |
| NPC — 필요할 때 참여 | 생성된 NPC의 초기화·등록·풀링 등 NPC 공통 실행 구조와의 연결이 적절한가? |

“모집은 성공했는데 UI가 실패로 표시한다” 또는 “모집 창을 다시 열 때 이벤트가 중복 등록된다”와 같은 문제는 각 담당이 내부만 보고 끝내면 놓칠 수 있다. 연결 계약의 평가 담당을 지정하고 주 담당이 확인 여부를 챙긴다. 이 예시는 평가 책임의 배분이며 실제 코드 소유권을 변경하거나 세 담당을 항상 별도 에이전트로 생성하라는 지시가 아니다.

## 6. 운영 항목 4 — 평가와 수정의 관계: 합의 완료

**평가 담당의 책임은 평가 후 기록까지다.** 문제의 위치·발생 조건·영향·근거와 수정 권고를 기록할 수 있지만, 직접 코드를 수정하거나 수정자를 선택·배정하고 수정 반복을 관리하지 않는다. 어떤 구현 스킬·작업자를 사용할지와 수정 실행의 조정은 `orchestrate-unity-work`가 맡는다.

### 요청에 따른 흐름

| 사용자 요청 | 진행 방식 |
|---|---|
| “모집 시스템을 평가해줘.” | 평가하고 결과를 기록·보고한 뒤 종료. 코드를 수정하지 않음 |
| “평가 후 수정해줘.” 또는 “평가하고 발견한 버그도 수정해줘.” | 평가·기록을 먼저 완료한 뒤, 사용자 요청에 포함된 수정 범위와 평가 결과를 바탕으로 `orchestrate-unity-work`를 사용. 평가자가 구현 조정을 겸하지 않음 |
| “보고서의 2번 문제를 수정해줘.” | 해당 문제와 필요한 영향 범위의 수정을 `orchestrate-unity-work`가 조정. 다른 지적까지 일괄 수정하지 않음 |

수정까지 이미 요청했다면 같은 범위의 수정에 대해 다시 허락을 묻지 않는다. 평가만 요청한 경우에는 문제를 발견했다는 이유로 수정 단계로 넘어가지 않는다.

### 버그 수정과 설계 변경의 구분

이벤트 중복 구독으로 모집이 두 번 실행되는 결함과, 모집 책임을 다른 클래스로 옮기자는 설계 개선은 구분한다. “버그도 수정해줘”라는 요청은 확인된 버그 수정을 포함하지만, 그 요청만으로 큰 구조 개편까지 수행하지 않는다. 요청 범위를 벗어나는 변경이나 미확정 게임 규칙의 결정이 필요하면 그 사항만 사용자에게 확인한다.

### 수정 후 확인의 범위

수정 단계의 오케스트레이터는 영향을 받은 부분의 확인과 기존 필수 검증·독립 리뷰를 조정한다. 예를 들어 이벤트 구독 수정은 중복 구독·해제와 관련 호출 흐름을 확인한다. 공통 계약을 변경했다면 영향을 받는 사용처까지 확인 범위를 넓힌다.

수정할 때마다 프로젝트 전체 평가를 처음부터 다시 수행하지 않는다. 필요한 컴파일·기존 검사·독립 리뷰는 유지하고, 입력이 바뀌지 않은 검사 결과는 재사용한다. 이 규칙은 평가 담당에게 수정 실행이나 검증 조정의 책임을 추가하지 않는다.

## 7. 운영 항목 5 — 결과 기록·통합과 재평가: 합의 완료

### 최종 보고서와 기록 위치

영역별 결과는 중복 지적과 상충하는 권고를 정리한 하나의 최종 보고서로 통합한다. 담당별 보고서를 그대로 이어 붙이지 않는다. 기본 기록 위치는 [Code_Evaluation_Result.md](../../Status/Code_Evaluation_Result.md)이며, 사용자가 별도 아티팩트를 요청하면 지정한 위치를 사용한다. 동일한 상세 결과를 여러 문서에 중복 관리하지 않는다.

| 보고서 항목 | 내용 |
|---|---|
| 평가 범위 | 대상, 평가 깊이와 날짜 |
| 확인한 범위와 한계 | 실제 확인한 코드·관련 구조, 미평가·미검증 사항 |
| 주요 판단 | 우선 수정할 문제와 이유, 근거가 있는 좋은 구조 |
| 개별 지적 | 위치·근거·영향·수정 방향 |
| 남은 확인 사항 | 결론을 내리지 못한 질문과 필요한 확인 |

짧은 평가는 위 내용을 간결하게 기록한다. 항목마다 별도 장문 문서를 만들거나 지적 개수를 채우기 위해 문제를 만들어내지 않는다.

### 지적의 성격과 중요도

| 구분 | 의미와 예시 |
|---|---|
| 확인된 문제 | 코드와 규칙 등의 근거로 문제를 확인함. 예: 창을 다시 열 때 이벤트가 중복 등록되는 경로 |
| 설계 개선 제안 | 개선 여지는 있으나 변경 비용과 이득을 비교해야 함. 예: 모집 화면과 모집 규칙의 결합 완화 |
| 추가 확인 필요 | 의심되는 문제가 있지만 현재 근거만으로 발생 조건 등을 확정하지 못함 |

명확한 규칙과 코드 근거가 있는 컨벤션 위반·책임 중복도 확인된 문제에 포함한다. 실행 오류만 문제로 취급하지 않는다. 중요도는 위 분류와 별도로 실제 영향과 수정 시급성에 따라 판단한다. 추가 확인이 필요한 내용을 확정된 심각한 결함처럼 보고하지 않는다.

각 지적에는 관련 파일·메서드, 판단 근거, 영향, 수정 방향과 확인 한계를 남긴다. 예를 들어 구독·해제 코드 검토로 중복 요청 가능성을 확인했어도 실제 플레이 재현을 수행하지 않았다면 그 한계를 명시한다.

### 과거 기록의 보존

- 이번에 다시 확인한 항목은 현재 근거와 상태를 갱신한다.
- 다시 확인하지 않은 기존 지적은 이전 평가일과 미재평가 상태를 보존한다. 일부 영역만 평가했다고 다른 영역의 날짜나 통과 여부까지 갱신하지 않는다.
- 수정됐다는 보고나 코드 변경 사실만으로 해결 처리하지 않는다. 기존 문제의 원인·발생 경로가 해소됐는지 확인한다.
- 이전 지적이 잘못됐음이 확인되면 지적 철회와 그 이유를 짧게 남긴다.
- 평가 범위의 완료 상태와 개별 문제의 해결 상태를 구분한다. 평가 완료는 문제 없음이나 수정 완료를 뜻하지 않는다.

### 재평가 절차

재평가는 요청 범위 안에서 기존 문제의 해결 여부와 현재 코드의 문제를 함께 확인한다.

1. 이전 기록에서 해당 범위의 지적과 당시 근거·발생 조건을 확인한다.
2. 현재 코드에서 기존 문제가 여전히 성립하는지, 원인·발생 경로가 해소됐는지 확인한다.
3. 수정으로 주변에 새 문제가 생겼는지도 확인한다. 예를 들어 중복 구독은 막았지만 창을 다시 열 때 구독이 복원되지 않는다면 기존 문제의 해결 여부와 새 문제를 각각 기록한다.
4. 항목별 결과와 확인 근거를 갱신한다.

| 재평가 결과 | 의미 |
|---|---|
| 해결 확인 | 기존 문제의 원인이나 발생 경로가 해소됐음을 확인 |
| 일부 해결 | 일부 경로는 고쳤지만 문제가 남는 조건이 존재 |
| 미해결 | 기존 문제가 현재도 성립 |
| 확인 보류 | 확인을 시도했지만 근거가 부족해 판단할 수 없음 |
| 미재평가 | 이번 범위에 포함되지 않아 확인하지 않음 |
| 지적 철회 | 이전 지적 자체가 잘못됐음을 확인 |

해결 확인에는 확인 방법과 한계를 함께 남긴다. 코드 검토로 확인한 것인지, 기존 검사까지 통과한 것인지 구분하고 수행하지 않은 플레이 검증까지 통과했다고 표현하지 않는다.

| 재평가 요청 | 확인 범위 |
|---|---|
| “모집 시스템을 다시 평가해줘.” | 모집 시스템의 기존 지적 해결 여부와 현재 구조를 평가 |
| “지난번 2번 문제가 해결됐는지만 확인해줘.” | 해당 문제와 수정 영향 범위만 확인 |

재평가를 이유로 무관한 영역까지 전체 평가하거나 모든 회귀 검사를 반복하지 않는다. 기존 기록을 추적 기준으로 사용하되, 평가·기록의 역할과 수정 조정의 역할은 6절에 따라 구분한다.

## 8. 합의 상태와 작성 시 확인 사항

| 순서 | 논의할 항목 | 현재 상태 |
|---|---|---|
| 1 | 평가 범위와 깊이 | 합의 완료. 위 3절을 기준으로 사용 |
| 2 | 에이전트 분담 기준 | 합의 완료. 위 4절의 독립적인 질문·조사량·중복 비용으로 판단 |
| 3 | 책임 경계의 세부 운영 | 합의 완료. 위 5절의 주 담당·필요한 교차 열람·경계 질문 담당·근거 기반 통합 규칙을 사용 |
| 4 | 평가와 수정의 관계 | 합의 완료. 위 6절을 따름. 평가자는 평가·기록만 수행하고, 요청된 수정은 평가 완료 후 `orchestrate-unity-work`가 조정 |
| 5 | 결과 기록과 통합 | 합의 완료. 위 7절의 단일 보고서, 지적 분류, 과거 기록 보존과 재평가 절차·상태를 사용 |

운영 항목 1~5번의 합의를 실제 스킬 작성 기준으로 사용한다. 이 문서의 기록 요청은 실제 스킬 작성 요청과 구분한다. 고정된 추가 조사 횟수, 수치화한 비용 한도와 새로운 심각도 등급 체계는 정하지 않았다. 예시를 임의의 수치 정책으로 바꾸지 않는다. 영역별 구체 문서 연결과 기존 스킬·보고서 형식의 반영 방법은 실제 작성 시 현재 파일을 확인한다.

## 9. 작성 시 유지할 프로젝트 제약

- 검증 비용이 과도해졌던 경험을 고려한다. 평가를 이유로 모든 검사나 전체 회귀 테스트를 반복하지 않는다.
- 기존 검사와 직접 검토를 활용하고, 입력이 바뀌지 않은 검사 결과는 재사용한다. 검증 전용 코드·테스트·하네스의 신설·확장은 별도의 명시 요청이 있을 때만 한다.
- 자동 Play Mode와 게임 화면 검증은 기본 절차에서 제외한다. 확인하지 않은 사항을 통과로 보고하지 않는다.
- 현재 작업 후보의 독립 리뷰를 맡는 `reviewing-unity-candidate`와 전체·선택 범위 평가 체계의 관계는 실제 작성 시 확인한다. 이 기록만으로 기존 필수 독립 리뷰를 제거하거나 두 리뷰를 항상 중복 실행하도록 바꾸지 않는다.
- 후속 합의는 이 문서에 누적한다. 실제 작성 시 확정 규칙과 필요한 변경 범위를 이 문서에서 확인하면 되며, 동일 내용의 별도 Plan 파일은 필요하지 않다.
